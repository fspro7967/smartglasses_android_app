# 朗读途中到达的新回复排在后面,不打断

上行音频每 3 秒成一段、每段各触发一次提问,所以「上一条回复还没念完,下一条就到了」是常态。
原来的代码在这种情况下直接覆盖朗读队列,造成旧回复被截断、计数错位。2026-11-11 修这个问题时
所有者选择:**新回复排在正在朗读的回复后面,念完旧的接着念新的。**

## 考虑过的选项

- **打断**:新回复到达即停掉旧的。响应最快,但一句话被切成两段时,第一段的回答会被第二段的
  回答掐掉。
- **排队**(选定):不丢任何一条回复。
- **丢弃**:朗读期间到达的回复直接不念。

## 后果

- 回复来得比念得快时,队列只增不减,助手会越来越滞后——念的是好几句话之前的回答。
  目前**没有上限也没有丢弃策略**,只有「停止」按钮能清空。
- 回传到开发板时,两条回复之间不会 `stop` 再 `play`,播放会话是连续的。
- 这个决定是在「每 3 秒一段、每段一问」的前提下做的。如果将来改成按一句话切段、或一轮只发
  一次请求(`.scratch/voice-pipeline/issues/04`),重叠本身会少很多,届时值得重新看这一条。
