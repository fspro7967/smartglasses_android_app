# 下行音频按 TTS 原生采样率发送,由开发板升采样

开发板的 I2S 固定 16 kHz,而 TTS 模型输出 8 kHz。最初的做法是手机先升到 16 kHz 再发
(32 KB/s),但 Qt 的 Android 蓝牙后端把每次特征写入串行执行,实测持续吞吐只有约 24 KB/s,
回传队列必然积压。现在的做法是:手机**直接发模型原生的 8 kHz**(16 KB/s),播放开始前用控制
指令 `rate:8000` 告知固件,固件做整数倍线性插值到 16 kHz。

决定体现在提交 `92749a5`(2026-10-04)与 `d36d8dc`(2026-10-05),此处是事后留档。

## 后果

- 带宽需求减半,对实测吞吐留出了余量。「约 24 KB/s」这个数字出自代码注释里记录的实测,
  换手机或 Qt 版本后可能不同。
- 固件只支持 16000 的**整数约数**(8000、4000、16000…)。模型采样率不满足时,
  `MainWindow::bleStreamSampleRate()` 退回 16 kHz 并在手机侧重采样——此时带宽又回到 32 KB/s,
  很可能再次积压。换 TTS 模型时要看它的采样率。
- 采样率是**播放会话**的一部分:固件在播放中拒绝切换,所以手机每轮播放都按
  `stop` → `rate:N` → `play` 的顺序发指令(见 `.scratch/board-esp32-link/issues/04`)。
- 不是开发板的设备(将来的眼镜)收到的也是原生 8 kHz,它期望什么采样率仍是
  `.scratch/ble-audio-out/spec.md` 第五节里待真机确认的问题。
