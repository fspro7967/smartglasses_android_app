# 08 — 朗读途中来了新回复,朗读队列被覆盖、计数错位

Status: resolved
Type: bug

## 问题

`MainWindow::speakReply()` 原来不管当前是否正在朗读,一律:

```cpp
m_speakQueue = splitSentences(reply);
m_speakIndex = 0;
m_sentencesOutstanding = 0;
```

而合成器里上一条回复的句子还在跑。它的 `sentenceFinished` 随后到达,会被记到新回复头上:
在途计数就此错位,朗读可能被提前判定为结束(开启回传时会提前给开发板发 `stop`,截掉尾音);
上一条回复则被拦腰截断,只剩已经合成出来的那一小段。

上行音频每 3 秒就可能触发一次问答(`issues/04`),所以「新回复到达时旧回复还没念完」是常态,
不是边角情况。2026-11-11 通读代码时发现,此前没有工单。

## 可选的行为(所有者 2026-11-11 选了 B)

- A. 新回复打断旧回复。
- **B. 新回复排在旧回复后面,念完旧的接着念新的。** ← 选定
- C. 朗读期间丢弃新回复。

## Answer

**2026-11-11 — 按 B 实现(代码在工作区,未经真机验证)。** 决策留档:
`docs/adr/0006-queue-overlapping-replies.md`。

`speakReply()` 在 `m_speaking` 为真时不再替换队列,而是:丢掉已经喂给合成器的前缀、
把新回复的句子追加到 `m_speakQueue` 末尾,在途计数原样保留。只有恰好停在「全部喂完、
只等音频排空」的收尾阶段,才主动推一把 `speakNextSentence()`;其余情况由正在合成的那句的
`sentenceFinished` 自然取走下一句。回传时开发板的播放会话不中断(不会在两条回复之间
`stop` 再 `play`)。

**这个选择的已知代价**:回复来得比念得快时,队列只增不减,助手会越来越「滞后」,
念的是好几句话之前的回答。目前没有上限,也没有丢弃策略;「停止」按钮会清空整个队列。
是否要加上限或改成一轮一答,和 `issues/04` 是同一个问题。

真机判据并入 `issues/11`。
