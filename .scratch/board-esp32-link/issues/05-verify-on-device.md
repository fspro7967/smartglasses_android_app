# 05 — 开发板真机验收

Status: ready-for-human
Type: task

只能在真机上判。前置:烧录的是本仓库 `firmware/esp32c3/` 的固件(已含 `issues/02` 的 MTU 与
无响应写、`issues/07` 的两处修正)。板子上若还是更早的固件,第 3 条必然失败。

> 2026-11-11 更新:判据第 2 条按现状改写(下行已改为 8 kHz + 固件插值),并新增第 8–11 条,
> 对应同日完成的 `issues/03`、`04`、`06`、`07`。

## 前置

1. 烧录固件(`cd firmware/esp32c3 && pio run -t upload`),打开串口监视器(115200),确认设备名 `ESP32_Audio`
2. 手机连上 `ESP32_Audio`,展开「蓝牙服务」
3. 若自动识别生效,状态行应显示「开发板: 扬声器(开启下方开关回传语音)」;
   特征列表里 `bebe…26a8` 不应能被设为输出(会被守卫拦回并提示)
4. 打开「语音回传眼镜」开关

## 判据

1. **上行**:对麦克风说一句英文,界面出现识别文本。
   若串口里 `mic:absent` 或没有音频包,是固件麦克风检测/接线问题,不是本仓库的问题。
2. **下行出声**:得到中文回复后,开发板功放应念出这句话,语速/音调正常。串口应依次看到
   `[控制] 收到: stop`、`rate:8000`(并打印「板上 2 倍插值」)、`play`。
   若听上去是半速慢放,说明 `rate:8000` 没有生效,固件仍按 16 kHz 解码手机发来的 8 kHz 数据。
3. **不溢出**:完整听一遍 30 秒以上的长回复,状态栏不应出现
   「已停止蓝牙音频回传: 蓝牙吞吐不足…」。
   若出现,把串口/`adb logcat` 里 `DeviceHandler::writeData ... chunkSize =` 的值记下来
   —— 这是判断 MTU 是否生效的唯一直接证据。
4. **停止跟手**:按「停止」后板子立即安静,而不是把已入队的几秒播完。
5. **重播**:按「重播」应重新走一遍 `play` → 音频 → `stop`。
6. **本机静音**:回传期间手机扬声器不应出声。
7. **自动配置的诚实性**(对应 `issues/03`):确认状态栏说的和实际一致 ——
   例如把开发板音频特征的 CCCD 拿掉后重连,不应再出现「麦克风通知已开启」,而应出现
   「发现开发板服务,但自动配置失败(麦克风音频特征无法开启通知),可在下方手动选择特征」,
   且状态行不显示「开发板: …」。
8. **`play` 要等确认**(对应 `issues/04`):正常情况下从回复到达至板子出声没有可感知的额外延迟,
   回复开头的字不丢。然后造一次失败:临时把固件里 `play` 的回执改成别的文本(或直接不回),
   重烧后触发一条回复——约 2 秒后状态栏应出现「开发板未进入播放态(等待 play 确认超时),
   语音改由本机播放」,回传开关自动关掉,**这条回复由手机扬声器从头念完**。
9. **意外断开后能干净地重连**(对应 `issues/06`):回传途中直接给板子断电。界面应回到未连接、
   回传开关关闭;板子重新上电后再次连接,应重新出现「已识别开发板 ESP32_Audio…」且回传正常,
   不需要重启应用。再做一次「断开后立刻连接」,界面不应被上一次连接迟到的断开事件冲掉。
10. **固件断开复位**(对应 `issues/07`):播放途中把手机蓝牙关掉,串口应打印
    「手机已断开,播放已复位,重新广播」;重连后的第一条回复开头不应带出上一次没播完的残音。
11. **上行不再爆音**(对应 `issues/07`):对着麦克风大声说话或拍一下,识别前的原始音频里不应有
    满幅跳变(有条件的话把上行存成文件看波形;没有条件就以识别结果是否正常为准)。

## 需要记录的数字

| 项 | 从哪里取 |
|---|---|
| 协商 MTU(chunkSize) | logcat 的 `DeviceHandler::writeData ... chunkSize =` |
| 30 秒回复是否溢出 | 状态栏 + logcat |
| 板子听感 | 正常 / 慢放 / 变调 / 断续 |
| 上行是否有丢包 | 串口 `audioCounter % 100` 日志与手机端识别结果对照 |
